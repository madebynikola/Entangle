## Model-Driven ARXML Generation from System Extracts via DaVinci API Automation

**Company:** DriveLogic Vojvodina d.o.o. works in automotive and mobility software. [C018] Challenge C018-CH1.  
**Researcher:** Mirjana Vidaković is a Full Professor in the Department of Computing and Control Engineering, Faculty of Technical Sciences. [R0948]  
**Format:** joint project, one page.

### The problem
DriveLogic Vojvodina manually produces approximately 3,200 AUTOSAR software component configuration files per project using two senior engineers over three weeks. [C018-CH1, C018] Competitors reportedly complete the same task in four days using automation, and the company is losing bids on price. [C018-CH1, C018] The company has access to the Vector DaVinci Configurator API documentation and two Python-capable engineers but lacks time to build the necessary tooling. [C018-CH1, C018] The company can dedicate one senior engineer at roughly 40% of their working week, provided the work is directly tied to tools or methods for active projects. [C018]

### Research questions
1. Can a metamodel-based parser reliably extract timing, port, and inter-runnable variable specifications from customer System Extract documents and map them to AUTOSAR software component schemas without manual intervention? Measured as the proportion of fields correctly mapped across at least 50 System Extract documents drawn from three completed DriveLogic projects, compared against senior-engineer-verified ground truth.
2. Can a template-driven generator invoking the DaVinci Configurator API produce a full project set of ARXML configuration files that pass Vector DaVinci validation checks, with engineers handling only flagged exceptions? Measured as the number of generated files passing DaVinci schema validation without manual correction, across two pilot projects run under the new tool.

### Approach
- Define an Ecore metamodel that captures the structure of DriveLogic's System Extract documents — timing constraints, port specifications, and inter-runnable variable declarations — using the metamodel authoring approach from the researcher's published work on AUTOSAR component descriptors.
- Author ATL model-to-model transformations that map parsed System Extract instances to AUTOSAR software component descriptor instances, following the ATL authoring and testing methods from the researcher's work on AUTOSAR toolchain pipelines, and measure transformation coverage on the company's historical data.
- Build a template-based synthesis layer using Ecore-based code generation techniques from the researcher's published work on RTE stub generation, adapted to emit ARXML artefacts conformant with the DaVinci Configurator's expected schema, with the Vector DaVinci API used as the invocation and validation layer.
- Apply OCL constraints and metamodel-level consistency checks — as used in the researcher's ARXML diffing and consistency-checking work — to flag semantic mismatches between the input System Extract and the generated ARXML before the file set is handed to an engineer.
- Integrate the pipeline into a Python-driven command-line tool that DriveLogic's engineers can run at project start, with an exception report listing only the files that require human review.

### First six months
- Week 1–2: Both sides sign the NDA and data-access agreement defining which System Extract and ARXML files can leave the company's premises and under what conditions. The company transfers anonymised or sanitised copies of System Extract documents and corresponding ARXML outputs from three completed projects to the researcher's Embedded Systems Laboratory.
- Week 3–4: The company's part-time engineer and the researcher hold a structured walkthrough of the three-project corpus to enumerate every System Extract element type present, flagging any proprietary extensions or customer-specific naming conventions that deviate from the AUTOSAR standard.
- Month 2: The researcher drafts the Ecore metamodel for the System Extract format. The company's engineer reviews it for completeness against active-project documents. The metamodel is versioned in a shared repository.
- Month 3: ATL transformation rules are authored for the highest-frequency element types (timing constraints and port specifications first). Each rule is unit-tested against the three-project corpus. A coverage report is produced showing which element types are handled and which remain.
- Month 4: The researcher prototypes the first DaVinci API calls — loading an ARXML skeleton, populating one software component descriptor, and running DaVinci's built-in schema validation — on one project's data. The output is reviewed by the company's engineer against the manually produced ground truth for that project.

### Agreed up front (proposed)
- Publication: results may be published in academic venues after a 60-day written review period during which the company may request removal of any content that reveals proprietary System Extract formats, customer-specific naming conventions, or project-identifying data. The researcher's methods, metamodel structure, and transformation approach may be published freely once proprietary content is redacted.

- Ownership of code: the source code of the tool is owned by DriveLogic Vojvodina. The researcher retains the right to publish the method and architecture, and to reuse the general-purpose metamodel patterns in other projects not involving the company's data.
